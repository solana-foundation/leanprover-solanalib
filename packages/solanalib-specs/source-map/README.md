# Source review registry

The parent [source-map.json](../source-map.json) selects the fragments present
in this checkout. `libraries.json` groups SDK models by library and function;
`foundation.json` records shared module reviews, and `applicability.json`
records source versions and build conditions. The `api` and `models` records
define the exact modeled subset. A library namespace does not imply coverage
of the whole crate. The loader
rejects duplicate identities, missing fragments, unlisted JSON fragments and
linked inputs.

These are review inputs. Complete declaration lists and audit results are
generated from Lean instead of being committed a second time.

`tools/generate_capabilities.py` uses these same model records to generate the typed catalog of each
library and the separate common supporting catalog. Members
retain the exact contract or complete family, reference, model identity, scope
and [Rust identities](#rust-identities). `--check` rejects stale generated bytes.
Capability modules have ordinary reviewed hashes; they add no duplicate model or
source records.

| Section | Recorded information |
| --- | --- |
| `packages` | Public upstream repository and an immutable Git revision or published archive checksum for each exact crate version. |
| `interfaces` | Source IDs, crate-relative paths, complete file hashes, source anchors and layout evidence. |
| `abstractions` | Exact hashes of reviewed production modules, source IDs, correspondence arguments and limitations. |
| `models` | Contracts, references, closed correctness and satisfiability witnesses, and finite execution evidence where required. |
| `api` | Exact Rust names, source anchors, model IDs, mathematical clients, scope and open implementation obligations. |
| `compatibility` | Reviewed releases sharing a contract, source arguments and known behavior differences. |
| `applicability_sources` | Published archives and checksums, or exact git origins, indexed by source and reviewed release. |
| `applicability` | Per-model source/version/build alternatives, defining Rust identities, interpretation conditions and evidence. |

A review covers all contents of its hash-pinned modules. The audit inspects
every constant in every registered production and test module, including
private declarations. It rejects unregistered source contracts, missing
module reviews, changed module contents and unapproved axioms. Witness
closedness and exact compiled contract, reference and sample identities are
checked from their types.

Schema 3 uses these fixed defaults to omit repetition:

- Rust implementation proof status is always open. The default kind of a model is
  `full`; assumptions, model gaps and remaining model requirements default to
  empty lists. A full model with recorded gaps is rejected. Here `full` describes
  the registered function model under its premises, not crate-wide coverage.
- For `x_contract`, the default reference is `x_run`, correctness witness is
  `x_reference`, and satisfiability witness is `x_satisfiable`. Explicit
  `reference`, `witness` and `satisfiable` fields override those names. Defaults
  never manufacture a declaration or proof.
- `witness_kind` is required. `Holds` and `FamilyReference` require
  `x_has_execution` unless `execution` names another witness. A family also
  requires `x_sample` unless `sample` names another one. A total `RealizedBy`
  reference cannot register an unrelated relation execution witness.
- A reference may name an exact `projection` and a closed named `receiver`.
  The audit checks those identities in the witness type; a different but
  definitionally equal field or receiver does not substitute for them.
- An API defaults to `contracted` and the model with its own ID. Empty client
  and dependency lists are omitted. `rust_names` records the source symbols;
  crate name and version come from the source record of the API. Both define the Rust identities of the
  catalogs below.
- Source identities come from the crate pin. A Git pin supplies the revision and
  a repository path formed from `path_prefix` and the crate-relative `path`. An
  archive pin supplies the exact published package, version and archive checksum.

## Rust identities

`rust_identities` in `tools/model-audit/solana_source_map.py` derives the identities of each
model, and the generator writes them as `Catalog.identities`, a
list of `RustIdentity` records with these fields:

| Field | Source |
| --- | --- |
| `crateName` | The crate of the API source record without its version, such as `solana-address`. |
| `crateVersion` | The version of that crate, such as `2.6.0`. |
| `item` | The item through which the function is called, derived from the Rust name. |
| `implementation` | The Rust name itself. |

Record each Rust name using the selected implementation identity: the Rust path at the definition, including generic parameters, such as
`solana_account_view::Ref::<'a, T>::try_map` or
`<solana_address::Address as core::convert::AsRef<[u8]>>::as_ref`. Do not include build-specific disambiguating suffixes such as ` [..]`, crate IDs or `{impl#N}` numbers in these registry paths. A binding must separately identify the exact dependency instance and implementation in its build. A method of a trait implementation, `<X as path::Trait<A>>::m` or `module::<impl path::Trait<A> for X>::m`,
is called through the item `path::Trait::m`. Any other name is its own item:
inherent methods, including `<impl X>` blocks, free functions and provided trait
methods. The derivation rejects other forms rather than guess.

A model lists the identities of every API that names it, for every Rust name,
in registry order and without repetition. A model with no API, or whose APIs
record no Rust name, lists none and admits no source-call entry. Identities
record no generic instantiation; several implementations of one type-indexed
family appear as separate identities without an index.

The [package guide](../README.md#build-and-audit) describes the source and witness audits; [BINDINGS.md](../BINDINGS.md) states the obligations for relating a registry identity to a Rust call.


A contract reused across exact source releases keeps one library root. By default,
a source-call registration requires an explicit normalized profile at that package
and release with the exact item and implementation. Missing profiles, extra names
and reexport-only identity transfers are rejected. The caller must still select
an eligible full build; registration does not discharge feature, target or
dependency facts. Members without source-call names remain mathematical capabilities.

An exception retains source metadata for a validated `partial` model with nonempty
API `rust_names`, a direct `profiles: []` record and no `consumers`. Its source names
remain in the unfiltered catalog as mathematical contracts with explicit premises. The model
contributes no identities to `Catalog.forBuild` for any build. A missing record or
consumer inheritance does not qualify. Relating source values to runtime values, matching the source and ABI, and proving Rust implementation correctness remain separate obligations.


## Function version compatibility

Every model has an `applicability` entry. A direct entry contains alternative
profiles; a source-less helper instead names its model consumers. Consumer
inheritance never copies the Rust call identity of a consumer. The top-level
`applicability_scope` records shared interpretation boundaries once.

Each direct profile selects an `applicability_sources` origin, explicit reviewed
`releases` and one or more `items` mappings, each with its own reference subset,
item and implementation path. Profiles retain a source `argument`, immutable
`evidence` and existing interpretation `conditions`. The argument covers
relevant types, reached dependencies, errors, state effects and configuration
branches; equal function text alone is insufficient. Predecessor names and
reexports require explicit mappings. The `identity_dependency` of a reexport names
the constrained, actually resolved package that defines its Rust identity.

Behavior-changing `target`, `features`, `target_features` and `dependencies`
constraints carry a reason. Do not require irrelevant build facts. Dependency
constraints describe the observable behavior of the selected library, not additional
callee proof obligations for its clients. Match package origins as well as
versions; a git fork is distinct from crates.io even when its version matches.

An item mapping or dependency requirement can additionally declare
`compatible_ranges: [{ "lower": "1.5.3", "upper": "2.0.0" }]`.
These intervals include the lower bound and exclude the upper bound. Each
needs a reviewed reference inside it and stays within one Cargo compatibility
line: `1.x` ends at `2.0.0`, `0.10.x` at `0.11.0`, and `0.0.3` at `0.0.4`.
They apply only to the recorded registry origin. Prereleases require explicit
reviewed entries; build metadata does not affect range membership. Split
intervals around known behavioral exceptions. Keep `releases` and archive
checksums as review evidence rather than manufacturing entries for the range.

The profile argument and dependency reasons identify the behaviors assumed
compatible: operations at the used types, results, errors and relevant effects.
SemVer is evidence for that assumption, not a guarantee of unspecified details
such as diagnostic text. Native fixtures retain their exact tested lockfiles.
No new callee contract is imposed on the modeled caller of the API.

Registry item ranges preserve every classification in the recorded release
census, including gaps and definition-path changes. Keep `0.0.x` and the yanked
Borsh `0.11.0` as exact references. Dependency references are reproducible
examples: extend them only under the recorded operation-specific preservation
assumption, and retain known behavior boundaries such as TLV resolver `0.11.4`
and the `3.1.0` allocation change of the Token-2022 interface. A git package may have
compatible registry dependencies without widening its own source revision.

`tools/version_compatibility.py` normalizes this registry into the installed
`applicability.json` and generates [the function table](../VERSION_COMPATIBILITY.md).
`tools/generate_capabilities.py` emits the same profiles as typed Lean data.
The installed lookup reports eligible, unsupported or unresolved per model;
`Catalog.forBuild` gives eligible source-call members their reviewed defining
identities while preserving their complete families. A reviewed observation
without a source-call registration remains unbound. See
[the build schema and usage](../BINDINGS.md#selecting-a-reviewed-build).

The separate `compatibility` records preserve source reviews for releases that
share a contract. They name `models`, a reviewed release window and a source
argument; optional `differences` retain pinned source anchors. When a group
contains distinct declarations, generated Lean controls compare their **entire**
contracts, including preconditions and finite outcomes. Consolidated groups
refer to one declaration. Neither case substitutes for source review of each
additional release.

Without `compatible_ranges`, displayed ranges only abbreviate the listed
reviewed releases; they supply no implicit fallback. `--fetch-index` checks
the recorded release census and immutable evidence against crates.io, including
yanked releases. This is independent of range-based eligibility and does not
claim that future releases were reviewed. Regenerate catalogs and installed
outputs after changing either reviewed evidence or declared coverage. Preserve
the complete contract; a different behavior needs a different profile or model.

`load_source_map` in `tools/model-audit/solana_source_map.py` expands these entries
to the checker representation. Schema 2 remains accepted for isolated audit
controls. Receipts seal the index and all fragments, so either a selection or
content change invalidates the previous receipt.

The compact registry retains source hashes, pinned revisions, anchors and the
limits of each correspondence argument. `check_solana_specs.py --fetch-sdk`
independently checks the pinned files and API anchors. These checks establish
source identity and mathematical evidence, not Rust body correctness, compiler
layout or runtime refinement. See [the package guide](../README.md) for the
complete validation commands and [binding obligations](../BINDINGS.md).

For the uncommon published crate whose source uses CRLF while the immutable
Git file uses LF, an interface may declare
`"repository_bytes": {"sha256": "<Git file SHA-256>", "transform": "lf-to-crlf"}`.
Its ordinary `sha256` still seals the untouched published source bytes.
Fetching verifies the Git digest, rejects any carriage return in that file,
replaces each LF by CRLF and verifies the published digest before staging.
Checking a local published source verifies both digests and the exact inverse
byte equation. No other normalization or transform is supported. Without this
explicit declaration, byte-for-byte equality is required.

A package can use an immutable published archive as its source:

```json
"source_archive": {
  "kind": "crates-io",
  "package": "example-sdk",
  "version": "1.0.0",
  "sha256": "<locked published archive SHA-256>"
}
```

Keep the public upstream `repository` as the project link. The archive identifies
the source independently of Git. A package with an additional public Git pin may
also record `revision` and `path_prefix`; otherwise omit those fields and any
interface `path_in_repository` or `repository_bytes` fields. A package must have
at least one complete source pin.

The package and version must exactly reconstruct the crate key. Retrieval uses
only `https://static.crates.io/crates/<package>/<package>-<version>.crate`.
The loader supplies the exact `<crate>/<path>` archive member of each interface;
interfaces cannot override the package declaration. Schema-2 audit inputs must
spell that exact `member` inside `source_archive`. Admission checks the complete
declaration, canonical relative path, exact crate identity and checksum syntax,
and rejects inconsistent declarations for the same crate.

Fetching authenticates the compressed archive before reading its contents in
memory, then verifies the existing `sha256` of every selected file before staging
any file from that archive. It never calls tar extraction to the filesystem.
Compressed data is limited to 32 MiB, expanded tar data to 128 MiB, each member
to 16 MiB and the archive to 10,000 members. The reader rejects malformed gzip
or tar, noncanonical or duplicate paths, members outside the exact crate,
links, special or sparse files, missing selected files, and mismatched hashes.
Selected members must be regular files. No byte normalization is performed.
Existing `repository_bytes` equations, if separately declared, still check the
unchanged published bytes. An absent archive declaration preserves the existing
Git route; an archive error never falls back to Git or another release.
